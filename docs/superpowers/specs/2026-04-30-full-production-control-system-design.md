# Full Production Control System Design

**Date:** 2026-04-30
**Status:** Draft for approval
**Scope owner:** AirMentor engineering
**Boundary:** Build the production-readiness control plane and prove it with synthetic mock-data dry runs that are deleted after verification. **No real student/faculty data is ingested by this work.** Real-college go-live remains gated by external institution, legal, security, and operations approvals that are out of scope.

---

## 1. Intent

### 1.1 Problem

AirMentor today exposes mock cohort data the moment the backend boots. The backend `dev:seeded` entry calls `seedIntoDatabase()` which unconditionally invokes `seedMsruasProofSandbox()` (`air-mentor-api/src/db/seed.ts:666-669`). That seeds the proof MSRUAS branch, ten proof faculty, 120 trajectory students, mentor assignments, offerings, and audit/timetable rows before any sysadmin action.

Effects:

- The system-admin overview shows mentor-gap, student, faculty, and branch counts before any simulation has been started.
- Seeded HOD/Course-Leader/Mentor identities (e.g. `kavitha.rao`, `devika.shetty`) can log in even though no proof simulation is active, then see mostly empty surfaces because data is gated on `activeProofSimulationRun`. Identity provenance and data provenance disagree.
- Production readiness blockers (real-data import gates, retention/export, CERT-In runbook, model governance, load/rollback drills) remain documentation only. There is no enforced control surface.

### 1.2 Goal

Deliver a complete production-control system with intent and evidence as first-class data, without ingesting real institutional data. Provide an end-to-end mock verification path that runs the production flows on synthetic data and deletes that data after verification, leaving zero residue.

### 1.3 Non-goals

- Real student or faculty data ingestion.
- Real-cohort historical model validation.
- Final production hosting selection.
- Legal, privacy, or CERT-In policy approval.
- Replacement of existing demo proof workflows. The proof sandbox remains, but only when a sysadmin explicitly creates a proof run.

## 2. Core Principle: Intent Front And Centre

Every production-sensitive action must answer eight fields before it can proceed:

- **Intent type:** what category of action is this.
- **Reason:** human-readable purpose entered or generated by the actor.
- **Actor:** user ID, faculty ID, role grant ID.
- **Authority:** required role(s), enforced server-side.
- **Provenance:** where did the inputs come from (`seed-demo`, `mock-verification`, `real-import-not-yet-supported`).
- **Environment:** `production`, `staging`, `verification-sandbox`, or `seed-demo`.
- **Decision:** `pending`, `accepted`, `rejected`, `committed`, `rolled-back`, `cleaned`.
- **Evidence:** audit event IDs, telemetry IDs, manifest IDs, artifact paths, cleanup proof.

These fields are persisted in the intent ledger (Section 4) and surfaced in evidence exports (Section 7).

## 3. Architecture Overview

### 3.1 Subsystems

1. **Production intent ledger** — append-only intent and evidence backbone.
2. **Seed and provenance separation** — boot-time seed limited to platform skeleton; mock cohorts created on demand.
3. **Login provenance gate** — login allowed only if identity provenance matches available data provenance.
4. **Import control plane** — manifest, dry-run, approval, commit, rollback metadata; production commits remain blocked but evaluable.
5. **Mock verification sandbox** — sandbox-scoped commit and cleanup that proves the production flow end-to-end.
6. **Evidence export and retention controls** — admin-only export of audit, telemetry, manifests, intents, governance reports, with redaction.
7. **Readiness endpoint and posture report** — production-like configuration checks and blocker summary.
8. **Model governance runtime** — explicit synthetic-vs-production-eligible model card.
9. **Operational drill registry** — load, backup, restore, rollback, alert, and browser drill records.

### 3.2 Component map

- Backend modules: `air-mentor-api/src/modules/production-control-plane.ts`
- Backend libs:
  - `air-mentor-api/src/lib/production-intent-ledger.ts`
  - `air-mentor-api/src/lib/production-import-control-plane.ts`
  - `air-mentor-api/src/lib/production-mock-verification.ts`
  - `air-mentor-api/src/lib/production-evidence-redaction.ts`
  - `air-mentor-api/src/lib/production-readiness-checks.ts`
  - `air-mentor-api/src/lib/production-model-governance.ts`

- Migrations under `air-mentor-api/src/db/migrations/`.
- Tests under `air-mentor-api/tests/production-*.test.ts`.
- Operator docs under `docs/readiness/` already exist; this design does not replace them.

## 4. Production Intent Ledger

### 4.1 Schema

Table `production_intents`:

- `intent_id` text primary key
- `intent_type` enum text:
  - `mock_import_verification`
  - `real_data_import_attempt`
  - `audit_export`
  - `retention_review`
  - `readiness_check`
  - `model_governance_review`
  - `load_drill`
  - `backup_drill`
  - `restore_drill`
  - `rollback_drill`
  - `proof_run_lifecycle`
  - `seed_lifecycle`
  - `login_provenance_decision`
- `environment` text: `production` | `staging` | `verification-sandbox` | `seed-demo`
- `actor_user_id` text nullable
- `actor_faculty_id` text nullable
- `actor_role_code` text nullable
- `reason` text not null
- `scope_json` text not null (academic scope or system scope)
- `provenance` text not null: `seed-demo` | `mock-verification` | `real-import-not-yet-supported`
- `status` text not null: `pending` | `accepted` | `rejected` | `committed` | `rolled-back` | `cleaned`
- `evidence_json` text not null (links to audit events, telemetry IDs, manifest IDs, artifact paths)
- `created_at` text not null
- `updated_at` text not null

Append-only at the application layer: `update` is allowed for status transitions and evidence appending, but `delete` is forbidden.

### 4.2 Service surface

Module `production-intent-ledger.ts` exports:

- `createIntent(input): Promise<{ intentId: string }>`
- `transitionIntent({ intentId, newStatus, evidencePatch }): Promise<void>`
- `attachEvidence({ intentId, evidence }): Promise<void>`
- `listIntents({ filter, limit }): Promise<IntentRow[]>`
- `getIntent({ intentId }): Promise<IntentRow>`

Every transition emits an `audit_events` row with `entityType='ProductionIntent'`, `entityId=intentId`, `action=<status>` and `metadataJson` linking the prior status.

### 4.3 Audit linkage helper

Helper `recordIntentBackedAudit({ intentId, audit })` ensures every intent-bearing mutation writes an audit row that references the intent and that the intent's `evidence_json.auditEventIds` array includes the new audit event ID.

## 5. Seed And Provenance Separation

### 5.1 Decision

The boot-time seed at `air-mentor-api/src/db/seed.ts:seedIntoDatabase` will only seed the platform skeleton needed to operate AirMentor:

- One institution row.
- Two demonstration departments (`dept_cse`, `dept_ece`) and two platform branches (`branch_cse_btech`, `branch_ece_btech`).
- The system administrator account `sysadmin` (already in `platform.seed.json`).
- Role templates and policy defaults.

It will **not** call `seedMsruasProofSandbox()` automatically.

### 5.2 On-demand cohort seed

The `seedMsruasProofSandbox()` function is moved behind a sysadmin-triggered intent flow:

- Endpoint `POST /api/admin/proof-runs` (existing) gains a precondition step:
  1. Create a `seed_lifecycle` intent with `provenance='seed-demo'`.
  2. If the proof cohort (department, branch, faculty, students) already exists for the requested batch, mark the intent `accepted` with `evidence.cohortAlreadyPresent=true` and proceed to enqueue the run.
  3. Otherwise, run `seedMsruasProofSandbox()` inside a transaction, write `provenance='seed-demo'` and `seed_intent_id` columns onto every newly inserted students/faculty/role-grant row, transition the intent to `committed`, and emit one consolidated audit event referencing the intent.
- Existing `POST /api/admin/proof-runs/:simulationRunId/stop` is extended:
  1. Open a `proof_run_lifecycle` intent with `provenance='seed-demo'` and `reason='proof-run-stop'`.
  2. Run the existing credential and session sweep.
  3. Run a cohort cleanup pass: delete proof faculty rows, role grants, ownerships, students, mentor assignments, offerings, simulation rows, observed-state rows, audit-event scoping records, and any other rows tagged `seedIntentId=<intent>`.
  4. Verify zero residue by querying the same scope and assert count = 0; transition intent to `cleaned`. If residue is non-zero, transition to `rejected` with `evidence.residual=...` and require operator action.

### 5.3 Provenance columns

Add nullable columns:

- `userAccounts.provenance` text
- `facultyProfiles.provenance` text
- `roleGrants.provenance` text
- `students.provenance` text
- `students.seedIntentId` text
- `facultyProfiles.seedIntentId` text
- `roleGrants.seedIntentId` text
- `mentorAssignments.seedIntentId` text
- `sectionOfferings.seedIntentId` text
- `simulationRuns.seedIntentId` text

Existing rows back-fill to `provenance='seed-demo'` for the platform skeleton (sysadmin and the two demonstration departments/branches), and `provenance='seed-demo'` `seedIntentId=null` for legacy proof-cohort rows on first migration. New rows always carry an explicit `seedIntentId`.

## 6. Login Provenance Gate

### 6.1 Rule

Login decisions in `air-mentor-api/src/modules/session.ts:registerSessionRoutes` are extended after credential and grant verification, before session creation:

1. If `activeRoleGrant.roleCode === 'SYSTEM_ADMIN'`, allow.
2. Else read identity provenance `roleGrants.provenance ?? facultyProfiles.provenance ?? 'seed-demo'`.
3. Run `evaluateLoginProvenance(identity)`:
   - If `provenance === 'seed-demo'`: require an active `simulationRuns` row whose `activeFlag === 1` and whose batch scope intersects the role grant's scope. If absent, reject with `403 DEMO_DATA_NOT_INITIALIZED` and a message instructing the actor to ask sysadmin to start a proof run.
   - If `provenance === 'real-import-not-yet-supported'`: reject with `403 REAL_DATA_NOT_INITIALIZED`. (This branch exists for forward compatibility; real ingestion is not in scope.)
   - If `provenance === 'mock-verification'`: allow only when `verification-sandbox` mode is active and the actor is sysadmin or a verification operator role grant (`SYSTEM_ADMIN` only for now).
4. Record a `login_provenance_decision` intent for every non-allow path with `evidence.identityRef`, `evidence.scope`, `evidence.reason`.

### 6.2 Effect

- Without an active proof run, `kavitha.rao`, `devika.shetty`, and other seeded HOD/CL/Mentor accounts cannot create a session, matching user expectation.
- Sysadmin remains the bootstrapper.

## 7. Import Control Plane

### 7.1 Manifest

Endpoint `POST /api/admin/production-imports`. Body schema:

- `importEnvironment`: `production` | `staging` | `verification-sandbox`
- `sourceSystem`: text
- `sourceOwner`: text
- `schemaVersion`: text
- `sourceChecksum`: text
- `rowCount`: integer >= 0
- `academicScope`: object `{ institutionId, departmentId?, branchId?, batchId?, termId?, sectionCode? }`
- `approvedBy`: text nullable
- `approvalEvidenceJson`: text nullable
- `intentReason`: text

Validation gates (`production-import-control-plane.ts:validateManifest`):

- `production` requires non-null `sourceOwner`, `sourceChecksum`, `approvedBy`, `approvalEvidenceJson`, and `intentReason`. Missing field → 400 with explicit field list.
- `verification-sandbox` requires `intentReason`; other production fields optional.
- `seed-demo` is rejected: seed lifecycle uses Section 5.

### 7.2 Dry-run

Endpoint `POST /api/admin/production-imports/:manifestId/dry-run`. Behaviour:

- Validate manifest is in `pending` state.
- Run row-level validation against `productionImportRows` rules: per-entity validators (students, enrollments, attendance, marks, faculty, mentor assignments) implemented in `production-import-control-plane.ts:rowValidators`.
- Persist row outcomes with `accepted` / `rejected` flag plus reason.
- Update manifest status to `dry-run-passed` if any accepted rows and zero schema violations; `dry-run-failed` otherwise.
- Emit an audit event linked to the manifest's `intentId`.

### 7.3 Commit

Endpoint `POST /api/admin/production-imports/:manifestId/commit`. Behaviour:

- `production` environment: reject with `501 PRODUCTION_COMMIT_NOT_IMPLEMENTED` and a structured payload listing missing real-data prerequisites. The endpoint exists so the gate is testable, but no real production write path is implemented in this scope.
- `verification-sandbox` environment: write to sandbox-scoped tables (Section 8) inside a transaction, transition intent `committed`, emit audit event, store rollback snapshot metadata.
- `staging` environment: defer; reject with `501 STAGING_COMMIT_DEFERRED`.

### 7.4 Rollback metadata

Every commit records a `productionImportRollbackSnapshots` row with `snapshotId`, `manifestId`, `intentId`, `scopeJson`, `tableSummariesJson` (counts before/after), and `createdAt`. The actual rollback execution is implemented for `verification-sandbox` only and is exercised by Mock Verification (Section 8).

## 8. Mock Verification Sandbox

### 8.1 Purpose

Run the full import → recompute → export → cleanup loop against synthetic data, prove zero residue after cleanup, and produce an evidence package. This is how we verify the production flow without using real data.

### 8.2 Data classes covered

The first iteration covers four families: students, enrollments, attendance, marks. Faculty, mentor assignments, offerings, and interventions are deferred to a follow-up plan because the proof sandbox already covers them indirectly.

### 8.3 Sandbox scope

The verification sandbox uses dedicated tables prefixed with `sandbox_`:

- `sandbox_students`
- `sandbox_student_enrollments`
- `sandbox_student_attendance_snapshots`
- `sandbox_student_assessment_scores`
- `sandbox_mock_intents`

Each row has `intentId`, `manifestId`, `provenance='mock-verification'`, and `createdAt`.

This isolation prevents the mock verification from polluting any production-shaped table even if the cleanup misbehaves.

### 8.4 Flow

1. Sysadmin opens a `mock_import_verification` intent with `environment='verification-sandbox'`, `reason`, and target scope.
2. POST a manifest with sample row payloads. The fixture generator `production-mock-verification.ts:buildSampleManifest` produces deterministic rows.
3. Run dry-run; expect mixed accept/reject outcomes that exercise validators.
4. Submit a corrected manifest; commit to the sandbox tables.
5. Optionally run a sandbox-scoped recompute that exercises the same risk scoring helpers used by the proof control plane (read-only against sandbox tables; no mutation of real proof tables).
6. Run an evidence export (Section 9) for the sandbox scope.
7. Run cleanup: delete sandbox rows, drop sandbox temporary objects if any, then verify all `sandbox_*` tables return count=0 for the manifest's scope.
8. Transition the intent to `cleaned` with `evidence.cleanupVerifiedAt` and `evidence.residualCount=0`. If residual > 0, transition to `rejected` and emit an alert event.

### 8.5 Acceptance

A green run produces an evidence package and ledger entry that prove:

- All validation gates fired.
- Approval path was exercised.
- Commit happened in `verification-sandbox` only.
- Recompute integration ran without touching real proof tables.
- Cleanup left zero residue.

## 9. Evidence Export And Retention Controls

### 9.1 Endpoint

`GET /api/admin/production-evidence-exports`. SYSTEM_ADMIN only.

Query parameters: `intentId?`, `intentType?`, `from?`, `to?`, `format=json`.

Response payload includes:

- Generated timestamp.
- Scope summary.
- Linked intents.
- Audit events (filtered by intent linkage).
- Operational telemetry events (filtered by name list configured per intent type).
- Import manifests and row outcomes.
- Readiness reports.
- Drill records.
- Model governance reports.
- Mock verification cleanup proofs.

### 9.2 Redaction

Module `production-evidence-redaction.ts:redactPayload` removes:

- Password hashes, password reset tokens, password setup tokens.
- CSRF cookie/header values.
- Session IDs (replaced with stable hashes scoped to the export).
- Bearer tokens and provider secrets.
- Email body and SMTP credentials.
- Free-text intervention notes flagged as sensitive.

A redaction summary (`fieldsRedactedCount`, `paths`) is included at the top of the export for verifiability.

### 9.3 Retention

Retention is configuration only in this scope. `productionRetentionPolicies` table stores per-record-family retention windows from `docs/readiness/data-retention-delete-export-policy.md`. A read-only endpoint `GET /api/admin/production-retention-policies` reports them. No automatic deletion job runs in this scope; the policy artifact alone is the gate evidence.

## 10. Readiness Endpoint And Posture Report

### 10.1 Endpoint

`GET /api/admin/production-readiness`. SYSTEM_ADMIN only.

### 10.2 Checks

- DB connectivity and migration status.
- `CSRF_SECRET` configured (`config.csrfSecretConfigured === true`) when origins are non-local.
- Cookie `secure=true` and `sameSite='none'` when origins are non-local.
- CORS origin list contains only allow-listed origins.
- Telemetry persistence dispatcher configured.
- Production intent ledger table reachable.
- Sandbox tables present.
- Seed/proof isolation: confirms `seedIntentId` columns exist and that no row in the production-shaped tables carries `provenance='real-import-not-yet-supported'`.
- Import control plane mounted.
- Evidence export mounted.
- Model governance current status.
- Outstanding readiness blockers list (from `docs/readiness/*` indexed by check name).

### 10.3 Output

Payload schema:

- `intentId`
- `generatedAt`
- `productionLikeMode`: boolean
- `checks`: array of `{ name, status: 'pass' | 'fail' | 'warn', detail }`
- `blockers`: array of `{ id, summary, ownerArea }`
- `evidence`: linked audit/telemetry/intent IDs

Failures emit a `readiness.report.failed` operational telemetry event with the failed check names.

### 10.4 Boundary

The endpoint never claims production readiness. It reports posture and blockers. A `productionReady` boolean is only `true` when all checks pass **and** the configured `blockers` list is empty. In this scope, the blockers list is non-empty by design, so the field is always `false`.

## 11. Model Governance Runtime

### 11.1 Endpoint

`GET /api/admin/model-governance/current`. SYSTEM_ADMIN only.

### 11.2 Logic

Module `production-model-governance.ts:evaluateModelGovernance` reads:

- `risk_model_artifacts` for active artifact metadata.
- `feature_schema_version`, `source_run_ids_json`, calibration metadata.
- Threshold approval metadata (currently absent; reported as `missing`).
- Subgroup/fairness review metadata (`missing`).
- Human-review policy metadata (`missing`).
- Real-data validation metadata (`missing`).

Status calculation:

- Default: `synthetic-demo-only`.
- `staging-validation`: requires real-data feature schema, calibration, and subgroup review.
- `production-eligible`: requires all gates above plus threshold approval, human-review policy, and rollback plan.

Until those gates exist, the endpoint returns `synthetic-demo-only` and the response includes the human-impact guardrail string from `docs/readiness/model-governance-card.md`.

### 11.3 UI surfacing

The system-admin dashboard already shows a model diagnostics strip. This design adds a dedicated row that reads the governance endpoint and shows `status`, `boundary`, `nextGates`, and `lastReviewedAt`. Nothing else changes in product UI.

## 12. Operational Drill Registry

### 12.1 Endpoint

`POST /api/admin/operational-drills` and `GET /api/admin/operational-drills`. SYSTEM_ADMIN only.

### 12.2 Drill record

Table `production_drill_records`:

- `drill_id` text primary key
- `intent_id` text
- `drill_type` text: `load` | `backup` | `restore` | `migration_dry_run` | `rollback` | `alert` | `browser`
- `environment` text
- `executed_at` text
- `executor` text (operator name or role grant ID)
- `outcome` text: `pass` | `fail` | `partial`
- `signals_json` text (latency, error rate, success metrics, missed alerts)
- `artifact_paths_json` text
- `notes` text

### 12.3 Pass/fail criteria

Inherited from `docs/readiness/load-test-plan.md`. The endpoint validates the payload but treats actual operational signals as opaque to AirMentor; the operator is responsible for correctness. A drill record contributes to readiness only after a sysadmin reviews it; an `acknowledged_by` field captures that.

## 13. Cross-Cutting Verification Standard

Every production-control endpoint or service must be covered by Vitest tests that prove:

- **Intent test:** the intent ledger row is created with correct fields.
- **Authority test:** non-`SYSTEM_ADMIN` callers receive 403.
- **Negative test:** missing required fields fail closed before any DB write.
- **Audit test:** `audit_events` row is emitted with `intentId` linkage.
- **Redaction test (export only):** secrets do not appear in the response body.
- **Cleanup test (mock verification only):** sandbox tables are empty for the manifest scope after cleanup.
- **Boundary test:** production-ready claim is never returned while blockers exist.

End-to-end Playwright tests cover:

- Sysadmin login and successful proof-run creation that triggers `seed_lifecycle` intent and seeds the proof cohort on demand.
- Non-sysadmin login is rejected with `DEMO_DATA_NOT_INITIALIZED` until sysadmin activates a run.
- Mock verification flow: create intent, dry-run, commit, recompute, export, cleanup, verify residual = 0.

## 14. Migration And Backwards Compatibility

### 14.1 Migration order

1. Add provenance/intent columns and the new tables in additive migrations. No destructive changes.
2. Backfill existing rows: platform skeleton rows keep `provenance='seed-demo'`, `seedIntentId=null`. Existing proof cohort rows are also marked `provenance='seed-demo'` so they remain visible to current demos until a sysadmin explicitly stops the proof run.
3. Stop calling `seedMsruasProofSandbox()` in the boot-time seed in a follow-up migration deployment that the implementation plan introduces in a single commit.

### 14.2 Behaviour at first restart after the change

- Existing demo databases keep working because the proof cohort is backfilled.
- New databases come up empty of proof data; sysadmin must start a proof run to populate it.
- Tests that depend on the proof cohort either start a proof run in their `beforeAll` or use the existing test helper that creates a run via the API.

---

## 15. Hard Boundaries

The system explicitly does not:

- Implement any path that ingests real student or faculty data.
- Claim CERT-In compliance, retention compliance, or fairness compliance.
- Promote a model to `production-eligible`.
- Run a real production load test or rollback drill.
- Replace existing proof control plane behaviour.

Every endpoint that could be misread as a production approval must include an explicit `boundary` string in its response that names this design document.

- Naming for sandbox tables (`sandbox_*` vs `verification_sandbox_*`).
